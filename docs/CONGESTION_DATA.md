## 0. 한 줄 결론

NextSpot은 현재 **무광고·무과금·비수익 공익형 관광 분산 실증 서비스이자 공모전 출품작**이다.
그러나 공개 웹서비스이고 상금 가능성과 향후 B2G·제휴 사업화 계획이 있으므로, 외부 데이터 제공자에게
일률적으로 `개인용` 또는 `비상업용`이라고 주장하면 안 된다.

업체에는 다음과 같이 정확히 설명한다.

> 현재는 광고·구독·데이터 판매가 없는 비수익 공익형 관광 분산 실증이며,
> 2026 관광데이터 활용 공모전 검증을 위해 공개 웹서비스로 운영합니다.
> 공모전 상금 가능성은 있으나 데이터 자체를 판매하지 않습니다.
> 향후 사업화는 별도의 상업 라이선스와 계약을 체결한 뒤에만 진행합니다.

NextSpot이 지금 구현할 수 있는 강한 약속은 다음이다.

> **지금 출발하면 도착할 때 어느 장소와 주변 구역이 상대적으로 덜 붐빌 가능성이 높은지,
> 데이터의 범위와 시각을 밝히고 대안을 추천한다.**

특정 카페의 빈 좌석 수나 식당의 정확한 대기시간은 POS·웨이팅·출입계수기·매장 CCTV 등
직접 데이터가 없는 한 제공하지 않는다.

## 1. 현재 서비스의 객관적 분류

| 질문 | 판단 | 이유 |
|---|---|---|
| 개인용인가? | **아니다** | 개인이 만들었더라도 공개 배포된 관광 서비스이고 실제 사용자를 대상으로 한다. |
| 현재 영리 서비스인가? | **아니다** | 현재 광고·구독·판매 수익이 없는 공익형 실증 단계다. |
| 모든 약관에서 비상업용인가? | **자동으로 그렇지 않다** | 공모전 상금, 공개 홍보, 향후 사업화는 공급자에 따라 영리와 간접 관련된 이용으로 판단될 수 있다. |
| 공익 서비스인가? | **그렇다고 설명할 근거가 강하다** | 혼잡 분산, 주민 생활환경 보호, 안전, 골목상권 수요 분산이 명확한 공익 목적이다. |
| 공모전 출품은 상업 이용인가? | **공모전 규정·데이터 약관마다 다르다** | 공모전은 개인 참가가 가능하지만 완성 서비스를 심사하고 상금을 지급한다. 공급자의 서면 확인이 최종 기준이다. |
| 향후 사업화가 가능한가? | **가능하지만 별도 계약 후** | 현재 실증 허가가 미래 상업 이용까지 자동으로 허용하지는 않는다. |

2026 관광데이터 활용 공모전은 개인과 기업 모두 참가할 수 있지만, 한국관광공사 OpenAPI를 활용한
`신규 관광 서비스`와 개발 완료된 완성 서비스를 심사하며 상금도 지급한다. 따라서 `집에서 혼자 쓰는
개인 도구`로 설명하는 것은 사실과 다르다.

공공누리의 상업적 이용금지 조건도 단순히 “현재 매출이 0원인가”만 보지 않는다. 공식 안내는
영리행위와 직접 또는 간접으로 관련된 이용을 금지한다고 설명한다. 그러므로 공익 목적은 협상에
유리한 요소이지, 라이선스를 면제하는 자동 통행증이 아니다.

### 외부에 사용해야 할 표현

- 좋은 표현: `비수익 공익형 실증`, `공모전 검증용 공개 파일럿`, `향후 사업화 시 재계약`
- 피할 표현: `완전한 개인용`, `어차피 비영리라 허가 불필요`, `공공 목적이므로 무료 사용 가능`
- 서면으로 확인할 항목: 화면 표시, 파생 등급 생성, 캐시, 보관기간, 공모전 발표자료 캡처,
  공개 사용자 제공, 향후 상업 전환

이 문서는 법률 자문이 아니다. 실제 계약 문구와 공모전 약관이 다르면 해당 문서가 우선한다.

## 2. 절대 바꾸지 않는 데이터 원칙

1. 카카오맵·구글맵·네이버의 인기 시간대 화면을 크롤링하거나 비공개 요청을 역분석하지 않는다.
2. 사용자 브라우저로 대신 수집하거나 화면 캡처·OCR로 우회하지 않는다.
3. 주변 주차·거리 유동을 매장 내부 혼잡으로 표현하지 않는다.
4. 상대 방문 추이를 `빈 좌석 12개` 또는 `대기 7분`으로 변환하지 않는다.
5. 관측 시각, 적용 반경, 출처, 장소 내부/주변 구분을 화면에 함께 표시한다.
6. 데이터가 없으면 `정보 없음`으로 두고 임의의 0.5, 0분, 가상 좌석 수를 만들지 않는다.
7. 데이터 제공자를 실제 제휴기관처럼 표시하지 않는다. 서면 제휴 전에는 `후보 공급원`이다.
8. 이메일·문의·계약 요청은 사용자의 명시적 승인 없이 에이전트가 대신 보내지 않는다.

권장 화면 표현:

```text
주변 150m 수요: 보통
14:20 관측 · 황리단길 거리 센서
이 장소 내부의 좌석 수나 대기시간을 의미하지 않습니다.
```

장소 단위 데이터가 실제로 있을 때만:

```text
장소 방문 추이: 평소 같은 요일보다 23% 낮음
14:00 집계 · 이동통신 기반 · 표본 신뢰도 보통
```

### 3.1 SKT Geovision Puzzle

공식 API에는 데이터 제공 가능 장소·상권 목록, 실시간·시간대별·통계성 장소/상권 혼잡도,
일자별 방문자 수와 유입력이 있다. NextSpot이 찾는 기능에 가장 가깝다.

한계:

- 경주의 모든 카페·식당을 지원한다고 보장하지 않는다.
- 단시푸딩 같은 소형 점포의 포함 여부는 장소 목록 API로 직접 확인해야 한다.
- 재배포·재판매는 영리·비영리를 가리지 않고 사전 문의 대상이다.
- 서비스 화면에 등급을 표시하거나 가공 점수를 만드는 권리도 서면으로 확인해야 한다.

2026-08-21 공개 요금:

| 요금제 | 공개 조건 |
|---|---|
| Free | 월 10건 |
| Basic | 33원/건, 일 100건 한도 |
| 해커톤 | 11원/건, 월 3,000건, 담당자 확인 필요 |
| 기업 | 사용량별 별도 계약·대량 할인 |

TMAP 묶음 상품에는 실시간 장소 혼잡도 단가가 별도로 보일 수 있으나 상품 호환성과 표시 권리는
반드시 SKT에 확인한다. TMAP Free의 장소 혼잡도는 2025년에 일 3건으로 축소 공지되었다.

호출비 예시만 계산하면:

| 시나리오 | 월 호출 수 | 8.8원/건 가정 | 33원/건 |
|---|---:|---:|---:|
| 100 DAU × 후보 3곳 × 30일 | 9,000 | 79,200원 | 297,000원 |
| 100곳 × 15분 × 일 12시간 × 30일 | 144,000 | 1,267,200원 | 4,752,000원 |

두 번째 방식은 Basic의 일 한도를 넘는다. 따라서 전 점포 상시 폴링보다 사용자에게 보이는 후보만
주문형 조회하고, 계약상 허용된 공유 캐시와 대량 계약을 조합해야 한다.

### 3.2 Loplat Footlab

Footlab 공개 화면은 당일 시간별 방문 추이, 지난주 같은 요일 대비 변화, 최근 28일 기반 예측,
표본 부족 시간대를 보여준다. 로플랫은 공식 소개에서 약 70만 장소와 700만 모바일 이용자의
Wi-Fi 기반 분석 데이터를 설명한다.

한계:

- 공개 Footlab 페이지를 긁어오는 것은 정식 API 계약이 아니다.
- 공개 SDK는 우리 앱 사용자 방문을 수집하는 도구이며, Footlab 전체 집계 피드를 구매할 권리와 다르다.
- 소형 점포는 표본 부족으로 값이 자주 비어 있을 수 있다.
- API·피드 가격은 공개되어 있지 않아 반드시 견적을 받아야 한다.

계약 시 요청할 내용:

- 황리단길 반경 상위 100개 장소의 ID 매칭 샘플
- 시간대 방문 추이, 지연시간, 최소 표본 기준, 결측률
- 앱 화면 표시와 파생 등급 생성 권리
- 캐시·보관·공모전 발표·서비스 공개 허용 범위
- 8~12주 제한 실증 가격과 이후 상업 전환 가격

### 3.3 ENCLE FlowEye

FlowEye는 Wi-Fi 센싱과 AIoT 장비로 공간 인구 흐름을 초 단위로 분석해 지도와 그래프로 제공한다.
관광공사 연구에서 황리단길을 IoT 방식으로 측정한 전례가 있어, 점포 내부가 아닌 `골목 100~150m
주변 수요`를 설명하기에 가장 적합한 후보이다.

확인할 핵심:

1. 과거 황리단길 장비가 지금도 운영되는지
2. 원시 또는 집계 피드의 현재 소유자와 사용권자가 누구인지
3. 기존 피드가 없다면 핵심 골목 5~8곳 재설치가 가능한지
4. API 형식, 지연시간, 공간 반경, 보관·재표시 권리

공개 가격은 확인되지 않았다. 센서 설치비나 운영비를 근거 없이 추정하지 말고 견적을 받는다.
관광공사 연구보고서가 공공누리 제4유형으로 표시되는 경우 보고서 자체는 출처표시·비상업·변경금지
조건을 지켜 참고자료로만 사용하고, 운영 데이터에는 별도 공급 계약을 체결한다.

### 3.4 경주 ITS 주차

현재 NextSpot이 실제 운영에서 확보한 가장 신뢰할 수 있는 실시간 관측이다. 10분 스냅샷으로
주차장별 총면·잔여면을 저장한다.

정기 수집은 Supabase Cron이 매시 `3,13,23,33,43,53분`에 호출하고, 3분 뒤 현재 버킷이
없을 때만 재시도한다. 외부 GitHub 예약은 수동 복구 전용이다. API URL과 기존 Render 관리자
토큰은 Supabase Vault에서 실행 시점에만 읽으므로 migration과 Cron 명령에는 비밀값이 없다.
수집 성공 여부는 Cron 작업 성공만으로 판단하지 않고 실제 10분 버킷 저장률과 HTTP 응답을 함께 본다.

사용 범위:

- 특정 매장의 내부 혼잡이 아니라 반경 내 주변 이동·주차 수요 신호
- 관측 후 30분 이내 도착에만 실시간 근거로 사용
- 장기간 축적 후 시간대·요일·행사·날씨를 결합한 주변 수요 예측 백테스트

### 3.5 한국관광공사 관광지 집중률 예측

공공데이터포털 서비스 `15128555`는 KT 이동통신 기반으로 관광지별 향후 30일 집중률을 제공한다.
가장 붐비는 시기를 각 관광지 내부에서 100으로 환산한 상대값이다.

- 비용: 무료
- 이용허락: 제한 없음
- 승인: 개발 자동승인, 운영 심의승인
- 개발 트래픽: 1,000회
- 올바른 사용: 같은 장소의 날짜·시간 변화, 미래 사전확률
- 잘못된 사용: 서로 다른 두 장소의 70과 40을 절대 혼잡 차이로 비교

2026-08-24 개발계정 승인을 완료하고 경주 향후 30일 전망 1,449행을 운영 DB에 적재했다.
수집기는 `totalCount`를 따라 전 페이지를 저장하며, 별도 승인 상품인 연관관광지 API가 실패해도
집중률 적재가 막히지 않도록 배치를 분리했다. 운영 일배치는 GitHub Repository Variable
`TOURAPI_INSIGHTS_ENABLED=true`일 때 실행한다.

### 3.6 KT·LG U+ B2B

관광·상권·생활인구 분석 상품은 존재하지만 공개 셀프서비스 방식의 경주 소형 점포 실시간 혼잡 API와
가격은 확인되지 않았다. 맞춤 분석·리포트·기업 계약에 가깝다. 장기적으로 유효하지만 공모전 직전의
핵심 도입 대상으로는 SKT·로플랫·FlowEye보다 느리다.

### 3.7 지도 서비스 인기 시간대

카카오 Local API는 장소명, 주소, 좌표, 카테고리, 전화번호와 카카오맵 상세 링크를 제공하지만
인기 시간대나 실시간 혼잡도 필드는 제공하지 않는다. Google Places와 네이버 지역검색도 공식
필드에서 인기 시간대 피드를 제공하지 않는다.

허용되는 방식:

- Kakao Local의 `place_url`로 보내 사용자가 최신 영업정보를 직접 확인
- 카카오와 정식 데이터 제휴
- 공식 API가 허용한 필드만 사용

허용되지 않거나 고위험인 방식:

- 인기 시간대 화면 크롤링
- 비공개 요청 역분석
- 사용자 브라우저를 수집 대행자로 사용
- 캡처·OCR로 자동 추출

이 상태에서 `실시간 가게 내부 혼잡을 이미 제공한다`고 홍보하면 안 된다. 현재 진실한 표현은
`실시간 주변 주차 수요 + 공공 관광 맥락 + 취향·보행시간 기반 대안 추천`이다.

## 10. 주차 실측 기반 시설 혼잡 추정 (`parking_derived`, 2026-09-08 추가)

`congestion_logs`에는 두 달 동안 실제 현장 관측이 사실상 한 건뿐이다(실측 2026-09-08:
7/02~7/09 시드 덩어리 + 8/21 낱개 1건). 그래서 관제 대시보드·히트맵·통계 리포트가 통째로
비어 있다. 반면 경주 ITS 공영주차 실측은 살아 있다(`area_demand_snapshots`, 10분 주기,
2,302행). **시연 마감까지 시설 단위 실시간 데이터를 구할 방법이 없으므로, 살아 있는 주차
실측에서 구역 혼잡을 계산해 시설별 추정치를 만든다.** 이 값은 시설 반경 2km 안 공영주차의
거리·규모 가중 점유율이고, 점유율을 혼잡도로 바꾸는 변환은 **하지 않는다**(보정할 근거가
없는 상태에서 곡선을 얹으면 추정이 조작이 된다). 그래서 이 숫자가 주장하는 것은 딱 하나 —
"이 구역의 공영주차가 이만큼 찼다"이고, 가게 안이 얼마나 붐비는지가 아니다.

§2의 3번 원칙(`주변 주차를 매장 내부 혼잡으로 표현하지 않는다`)을 지키는 방법은 값을 넣지
않거나, **넣되 파생임을 값과 함께 운반하는 것** 둘뿐이다. 여기는 후자를 택하고 표식을 세 겹
건다: `source='parking_derived'`(기존 값에 섞지 않아 나중에 골라낼 수 있다) ·
`evidence_tier='synthetic'`(학습 정답과 '지금 혼잡' 후보에서 자동으로 빠진다) ·
화면 라벨(관리자 대시보드가 `주차 실측 기반 추정`으로 표시하고 무엇에서 파생됐는지까지
적는다). 결과적으로 이 행들은 SPOT 점수·추천 순위·모델 학습 어디에도 닿지 않고, 값이
보이는 곳은 관리자 관제 화면뿐이다.

| 항목 | 값 | 근거 |
| --- | --- | --- |
| 원본 | `area_demand_snapshots` + `..._lots` (`gyeongju_its`) | 유일하게 살아 있는 실시간 관측 |
| 반경 | 2,000m | `parking_demand_service`·`area_demand_forecast_service`가 이미 쓰는 '주변' 경계 |
| 격자 | 0.005°(위도 약 555m·경도 약 450m) | 거리 가중 커널이 500m 스케일이라 더 잘게 나눠도 값이 갈리지 않는다 |
| 변환 | 없음(점유율 = 추정 혼잡도) | 보정할 실관측이 1건뿐이라 어떤 곡선도 근거가 없다 |
| 인원수 | 기록하지 않음(`current_count IS NULL`) | 점유율 → 인원 환산 계수가 없다 |
| 커버리지 | 활성 1,669곳 중 846곳(50.7%, 2026-09-20 실측) | 반경 밖 823곳에는 **값을 만들지 않는다** |
| 실행 | 관리자 수동 트리거 1회 | 자동 주기 적재는 되돌리기 어렵다(아래) |

주기 실행을 붙이지 않았다. 10분마다 쌓기 시작하면 하루면 이 표의 절대다수가 추정치가 되고,
그 뒤에는 어느 행이 언제 들어왔는지 다시 세어야만 되돌릴 수 있다. 붙인다면 (1) 부분 인덱스
`uq_congestion_logs_parking_derived`로 버킷당 1회를 이미 보장하므로 스케줄러는
`POST /api/v1/admin/congestion-estimates/parking-derived`를 그대로 호출하면 되고,
(2) 그 전에 이 표의 실측/추정 비율을 화면에 상시 노출하는 편이 안전하다.

- 구현: `apps/api/app/services/parking_derived_congestion_service.py`(산식·가드),
  `apps/api/app/routers/congestion_estimates.py`(관리자 트리거·미리보기)
- 스키마: `supabase/migrations/20260908120000_parking_derived_congestion_source.sql`
- 한계: 실시간 잔여면을 주는 ITS 주차장이 **4곳뿐**이고 그중 3곳이 황리단길 반경에 몰려
  있다. 즉 사실상 두 덩어리의 관측을 806곳에 펼친 값이다. 심사 설명에서 이 사실을 먼저
  말하지 않으면 커버리지 48.8%가 실제보다 두껍게 들린다.

### 10.1 서울 실측으로 보정한다 (구현 2026-09-20)

위 표의 "변환 = 없음(점유율 = 추정 혼잡도)"에는 이유가 있었다 — **보정할 실측이 없었다.** 주차는
어디까지나 임시 방편이다. 통신사 실시간 유동인구는 기업용 가격이라 지금 살 수 없고(§3.1·§3.6),
"공영주차가 이만큼 찼다"는 "사람이 이만큼 많다"가 아니다.

서울시 실시간 도시데이터는 그 **진짜 신호**(KT·SKT 기지국 5분 집계 기반 인구)를 무료로 준다.
그리고 서울 121곳 중 실시간 주차 대수까지 같이 주는 곳은 사실상 **명동 관광특구(5곳)·동대문
관광특구(8곳)** 둘뿐이다 — 경주 ITS 3~4곳과 자릿수가 같은 조건이다. 이 두 곳에서 "주차 점유율이
x일 때 실제 인파는 y였다"를 배워 경주 추정에 얹는다. 서울 실측이 경주 추정을 고치는 다리이고,
경주에 실시간 혼잡 데이터가 생기는 날까지의 최선이다.

| 항목 | 값 |
| --- | --- |
| 곡선 | 등장회귀(PAVA, [0,1] 20구간) → 꺾은선 knot. **단조 비감소** — 순위를 뒤집지 않는다 |
| 적용 | `level = f(0.7·주차 + 0.3·관광)`. 관측 범위 밖은 항등 쪽(위쪽 바깥은 절대 깎지 않는다) |
| 관문 | KST 3일 이상 · 짝지어진 10분 버킷 300개 이상 · **홀드아웃 MAE가 항등보다 엄격히 낮을 것** |
| 학습/평가 | KST 날짜로 분할(앞 날짜 학습 → 뒤 1/3 평가). 시간 순서 누수 금지 |
| 통과 전 | `f` = 항등. 값이 하나도 바뀌지 않는다. 서울 수집 시작 전인 오늘이 이 상태다 |
| 저장 | **없음.** `seoul_citydata_snapshots`의 결정적 함수라 읽을 때 적합하고 6시간 캐시한다 |
| 표시 | 원값(`raw_level`)·보정 여부(`calibrated`)·근거 문자열을 값과 함께 운반한다 |

시(hour)별 모양은 계산해서 **보여만 주고 적용하지 않는다** — 주차 성분이 이미 시간대 변동을
싣고 있어 한 번 더 곱하면 같은 변동을 두 번 센다.

- 구현: `apps/api/app/services/congestion_calibration_service.py`(적합·관문),
  `apps/api/app/services/congestion_estimator_service.py`(적용·출처 운반),
  `apps/api/app/routers/engine_validation_calibration.py`
  (`GET /api/v1/admin/engine-validation/seoul/calibration`)
- 한계: 서울은 대중교통 비중이 높아 주차의 설명력이 경주와 다르다. 곡선이 경주에서 과소 추정
  쪽으로 틀리면 [`CONGESTION_ENGINE_PLAN.md`](./CONGESTION_ENGINE_PLAN.md) §9의 "붐빔을 여유로"
  위험이 커진다. 그래서 관측 범위 위쪽 바깥에서는 값을 **깎지 않는 쪽**으로 굳혔다.

### 10.2 관제 대시보드의 '예측'·'시나리오' 라벨 (2026-09-22, 브라우저 전용)

§10의 추정도 실측이 쌓이기 전에는 자주 비어 있다(자정 직후·주차 원본 조회 실패, 그리고 추정 격자는
대표 관광지만 담으므로 다른 업종·아직 오지 않은 시간은 원래 값이 없다). 그래서 관제 대시보드(`/admin/dashboard`,
관리자만)는 비실측 어휘를 둘 더 쓴다. 둘 다 **화면 표시일 뿐이다** — API 응답·`congestion_logs`·
SPOT 점수·추천·학습 어디에도 닿지 않고, `?demo=1` 시연 화면과도 별개다.

| 어휘 | 정의 | 어디에 | 배지 |
| --- | --- | --- | --- |
| 실측 | 서버에 저장된 관측·기록(제보·좌석 방송·추천 기록·피드백) | 모든 패널 | 없음 |
| 추정 | §10 — 공영주차 실측 + 관광공사 집중률, 읽는 시점 계산 | 시설 혼잡 | `추정`(하늘색 점선) |
| **예측** | 업종별 시간대 곡선 × 요일 계수. 곡선 상수는 `apps/api/app/services/spot/industry_baseline.py`에서 숫자 그대로 옮겼다(웹 테스트가 파이썬 원본과 대조). 오늘 추정 격자에 섞인 칸에만 당일 추정 앵커를 곱한다(아래). 값은 95%를 넘지 않는다 — 예측이 만석으로 읽히지 않게 | 오늘 실측·추정이 없을 때의 시설 혼잡 전체(예측 단독 — 앵커 없음, 관광객 카드의 'AI 예측'과 같은 값), 추정 격자의 아직 오지 않은 시간·추정 대상이 아닌 업종, 실측 격자의 아직 오지 않은 시간(모두 빗금 칸) | `예측`(보라 점선) |
| **시나리오** | 고정 예시 하루 총량(`apps/web/lib/demoFixtures.ts`) × KST 시각 누적 비율 — 하루 동안 결정적으로 올라간다 | 혼잡 모델 입력이 없는 KPI: 수락률·DAU·재배치·절감 분·깔때기 | `시나리오`(호박색 점선) |

전환 규칙: 패널은 **집계 창에 실측 표본이 5건 이상**이면 실측을 보여 주고(`MIN_MEASURED_SAMPLES = 5`),
미만이면 가진 것 중 가장 높은 비실측 근거(추정 > 예측 > 시나리오)를 배지와 근거 한 줄
(`시나리오 · 도입 목표 패턴 × 시각 진행률 · 실측 3건 수집 중`)과 함께 보여 준다. 실측이 1~4건이면 그
건수를 그대로 적고(시설 혼잡은 추정·예측 배너와 평균 혼잡도 카드에 `현장 실측 3건 수집 중 · 5건부터
실측 전환`), 0건은 측정한 0이 아니므로 숫자로 적지 않는다.

**추천 고리 네 패널은 함께 전환한다**(2026-09-26 보정). 수락률(최근 7일 추천)·DAU(오늘 피드백)·
분산 효과(오늘 수락 — 재배치·절감 분)·깔때기(최근 30일 노출)는 같은 흐름(추천 → 수락 → 이동 → 평가)을
다른 창으로 센다. 패널마다 따로 바꾸면 실측 `5,000건 중 0건 수락` 옆에 시나리오 `179건 재배치(추천
수락)`이 서서 둘 중 하나가 거짓으로 읽힌다. 그래서 넷 중 하나라도 실측 5건 이상이거나 오늘의 브리핑
(실측 사실 문장)이 떠 있으면 넷 다 실측을 그리고(표본이 적은 패널도 실제 건수 그대로), 넷 다 5건
미만일 때만 시나리오를 그린다. 판정 전에는 로딩 모양이고, 조회에 실패한 패널은 판정에서 빠진다
(`resolveLoopBasis`). 추천 기록이 이미 쌓인 운영 DB에서는 이 네 패널이 실측으로 보인다.

시설 혼잡 블록의 순서는 오늘 실측 > 오늘 추정 > 오늘 예측 > 과거 실측일 > 없음이다(예측이 옛 시드 날짜
폴백보다 앞선다). 예측 칸은 값이 있는 칸을 덮어쓰지 않고, 행이 있는 시설의 지나간 시간 관측 공백은
`수집 중`으로 남긴다. 격자에 행이 없는 업종은 활성 시설(`is_active`) 중에서 골라 채우는데, 추정
격자·예측 단독이면 하루 전체를(그 업종은 오늘 값이 원래 없다), 실측 격자면 아직 오지 않은 시간만
채운다. 추정 앵커는 **지나간 시간 중 업종 곡선이 피크의 70% 이상인 시간만** 넣어 `mean(추정) ÷
mean(곡선)`으로 뽑고 0.5~1.2로 클램프한다 — 밤·새벽 칸을 넣으면 주차 점유율의 바닥값 때문에 비가
부풀어 앵커가 늘 상한에 붙는다. 추정 행이 있는 시설은 그 시설의 추정에서, 없는 업종은 추정 전체에서
뽑는다(그래야 한산한 곳의 다음 시간이 추정의 흐름을 잇는다). 같은 업종·같은 시각의 예측은 시설과
무관하게 같은 값이며, '예측 피크(이후 시간대)' 목록도 그런 시설들을 `음식점 12곳`처럼 한 줄로 묶는다.
서버가 응답하지 않으면 `갱신 중`이다 — 예측·시나리오는 **데이터의 부재**만 채우고 **서버의 부재**는
가리지 않는다. CSV 에도 행마다 `근거` 칸에 네 어휘를 글자로 적는다.

§2 원칙은 그대로다. 6번(`데이터가 없으면 정보 없음, 임의의 0.5·0분을 만들지 않는다`)이 금지하는
것은 **라벨 없는 값**이다 — 예측·시나리오는 배지와 근거 한 줄을 달고 관제 화면에만 놓이는 모델값이고,
관광객 화면에는 나가지 않으며, 예측을 실측이라 부르지 않는다. 3번(주변 주차를 매장 내부 혼잡으로
표현하지 않는다)도 그대로다 — 예측은 업종 패턴이지 매장 내부 관측이 아니고, 화면 문구도 그렇게 적는다.

- 구현: `apps/web/lib/adminPredictedView.ts`(곡선·앵커·격자 채움·시나리오·전환 규칙·추천 고리 공동 판정),
  `apps/web/lib/adminEstimateView.ts`(다섯째 근거 `predicted`와 배너 문구), 테스트
  `apps/web/lib/adminPredictedView.test.ts`
- 발표 대본·심사 답변: [`contest/DEMO_SCENARIO.md`](./contest/DEMO_SCENARIO.md) §2,
  [`contest/JUDGE_QA.md`](./contest/JUDGE_QA.md) Q11·Q16
