> 코드·데이터 구조로 옮긴 계획이다. 원칙의 정본은 [`CONGESTION_DATA.md`](./CONGESTION_DATA.md)이고,

## 0. 한 줄 요약

경주에는 실시간 유동인구가 없다는 사실을 화면과 발표에서 먼저 인정하고, **살아 있는 실측(경주 ITS 주차)과
공공 통계(관광공사 집중률)로 구역 혼잡을 추정하는 "추정 모드"**를 관광객 화면까지 연결한다.
같은 추정기를 **서울 실시간 도시데이터(121곳, 5분, 통신사 기지국 기반)가 있는 서울에서 실측과 대조**해
정확도를 숫자로 보여 주고, "실시간 혼잡 데이터가 연결되면 그대로 실사용 가능하다"를 서울 라이브 화면으로 증명한다.

## 1. 회의 결론 (2026-09-09)

- 통신사 실시간 유동인구(SKT·KT B2B)는 기업용 가격이라 배제한다. `CONGESTION_DATA.md` §3.1·§3.6의 후보는
  "사업화 이후"로 미룬다.
- 서울시는 통신사 데이터를 받아 **서울 실시간 도시데이터**로 무료 개방하고 있다. 이것을 **엔진 검증용 지역**으로 붙인다.
- 경주는 실시간 정보가 없음을 빠르게 인정하고, 대신 "혼잡도 정보만 연결하면 바로 실사용"이 가능한 구조임을 어필한다.
- 경주의 그날 총량은 관광공사 집중률 API에서, 구역별 분포는 실시간 주차장 데이터에서 만든다(추정 모드).

## 3. 목표와 심사 메시지

**주장하는 것**
- 경주 화면의 혼잡 색은 "실시간 공영주차 실측 + 관광 통계 기준선으로 계산한 **구역 추정**"이며, 관측 시각·반경·출처가 값과 함께 붙어 있다.
- 같은 추정기를 서울 N곳에서 M일 동안 실측과 대조한 결과가 대시보드에 있다(등급 일치율·위험 오분류율·30분 전망 오차).
- 서울처럼 실시간 인구가 들어오면 추정기 없이 그 값이 바로 `measured` 등급으로 흐른다(코드 경로가 같다).

**주장하지 않는 것**
- 경주 특정 가게의 내부 혼잡·빈 좌석·대기 분(§2 원칙 3·4).
- 서울 검증이 경주 정확도를 보장한다는 것 — "다른 도시에서 같은 산식이 이만큼 맞았다"까지만.

## 5. 설계

### 5.1 공통 추정기 — 한 산식, 두 지역

지역별로 다른 코드를 두지 않는다. 추정기는 "주차 신호 제공자 + 통계 기준선 제공자"를 주입받는 함수이고, 경주와 서울은
제공자만 다르다. 산식은 현재 `area_demand_service.py`·`parking_demand_service.py`·`parking_derived_congestion_service.py`가 이미 쓰는 것이다.

```text
parking_now(z, t) = Σ occ_i · w_i / Σ w_i        occ_i = 1 − 잔여/총면,  w_i = min(총면_i, 500) / (1 + dist_i / 500m),  dist_i ≤ 2km
prior_day(z, d)   = 앵커 관광지 집중률(d) / 100     상대지수 0~1 — 앵커는 이름 정확매칭 → 없으면 2km 거리감쇠
level_raw(z, t)   = 0.7 · parking_now + 0.3 · prior_day      (둘 중 하나만 있으면 그 값, 둘 다 없으면 None — 숫자를 만들지 않는다)
level(z, t)       = f(level_raw)                             f = 단조 보정. 서울에서 적합하기 전에는 항등(§10 원칙)
도착시점(t+Δ)     Δ ≤ 30분 → parking_now 그대로 · Δ > 30분 → 주차 이력 전망(area_demand_forecast_service)
```

- 0.7/0.3과 `f`는 **서울 검증이 결정**한다(§5.3). 알려진 이슈 ①("상대지수를 절대 점유율처럼 섞는다")은 이 검증으로 데이터를 놓고 닫는다.
- 인원수(`current_count`)는 어느 지역에서도 만들지 않는다.

**제공자 매핑**

| 입력 | 경주 | 서울 |
|---|---|---|
| 주차 실시간 | 경주 ITS(`gyeongju_its`, 10분 스냅샷, 실시간 4곳) | `citydata` `PRK_STTS`(대상지별 주차장 총면·현재 대수) |
| 통계 기준선 | 집중률 `areaCd=47, signguCd=47130` (적재 중) | 집중률 `areaCd=11`, 종로 `11110`·중구 `11140`·용산 `11170`·마포 `11440` — 수집기 파라미터화 |
| 정답(실측) | 없음 | `LIVE_PPLTN_STTS` 등급 + 인구 범위 |
| 구역 | §10 격자 0.005°(≈555m×450m) | 대상지(핫스팟) 자체 |

### 5.2 경주 추정 모드

지금은 `parking_derived` 행이 관리자 관제 화면에만 보이고, 추천·지도·학습 어디에도 닿지 않는다(§10). 추정 모드는 이것을
**관광객 화면까지** 연결한다.

| 항목 | 현재(§10) | 추정 모드 |

> 한두 시간 만에 넘고, 실측과 섞이며, 쌓기 시작한 날부터만 이력이 생긴다. 읽을 때 계산하면 **원본 30일 이력이 곧 추정 이력**이라
> 관리자 히트맵이 오늘 바로 채워진다. 구현: `apps/api/app/services/congestion_estimator_service.py`.
> - 대표 장소(히트맵 행) = 관광공사 집중률과 이름이 1:1로 맞은 관광지 중 주차 반경 안에 있는 곳(실측 10곳: 월정교·교촌마을·천마총 등).

> - 수동 적재 버튼(`parking_derived`)과 "24시간 모의 발생" 버튼은 관리자 화면에서 제거한다(D6, 이중 집계 방지).
>
> **반영(2026-09-20) — D2 구현 방식.** `scoring_mode='estimated_rules'` 는 **만들지 않았다.** 기존 `area_stats_rules` 가 이미 같은 산식
> (주차 0.7 + 관광 0.3, `area_demand_service`)을 대기 패널티로 순위에 반영하고 있어 새 모드는 같은 신호를 두 번 센다.
> 대신 (1) 추정은 화면 근거로만 싣는 별도 필드 `congestion_estimate` 이고 `congestion_source` 는 measured/predicted/none 그대로,
> (2) `area_stats_rules` 후보의 추정이 0.9 이상이면 실측 0.9 이상과 똑같이 계층 이점을 잃는 **강등 전용** 관문(`score.py` 4-2)만 둔다.
> 우선순위: 실측(사장 좌석 포함) > 학습 모델 예측 > 추정 > 없음. 지도는 별도 `GET /api/v1/congestion/estimates` 로 받는다.

### 5.3 서울 검증 — 수집 → 저장 → 지표 → 보정 → 전이

1. **수집**: `POST /api/v1/engine-validation/seoul/collect`(기계 호출, `require_machine_or_role`). 대상지 목록을 순회해 인구(10분)·주차(30분)를
   받아 10분 버킷으로 저장한다. 실패한 대상지는 건너뛰고 상태에 남긴다(경주 수집기와 같은 `_status` 패턴).
2. **저장**: 새 테이블 `seoul_citydata_snapshots`(대상지 코드·이름·버킷·`congest_lvl`·`ppltn_min`·`ppltn_max`·`fcst` JSONB·`prk` JSONB·`observed_at`).
   `congestion_logs`에는 넣지 않는다 — 경주 시설과 무관하고 정직성 제약(`source` CHECK)을 건드릴 이유가 없다. RLS는 service_role 전용, 읽기는 관리자 API.
3. **추정**: 같은 버킷에 대해 §5.1 추정기를 서울 제공자로 돌려 `level_est`를 옆에 저장한다(정답과 같은 행에 두면 지표 계산이 SQL 한 번이다).
4. **지표**: §6 표. 관리자 화면 `/admin/engine-validation`에 대상지별·기간별로 그린다.
5. **보정**: `level_raw` → 실측 정규화 인구(대상지별 관측 최대 대비 0~1)로 단조 회귀(등장회귀 또는 구간 선형)를 적합해 `f`를 얻고, 0.7/0.3도 격자 탐색으로 정한다.
   학습·평가는 날짜 단위로 나눈다(시간 순서 누수 금지 — `area_demand_forecast_service`와 같은 규칙).
6. **전이(결정 D5)**: 서울에서 적합한 `f`·가중치를 경주에 쓴다. 쓴다면 화면 라벨에 "서울 실측으로 보정"을 덧붙이고, 안 쓰면 항등을 유지한다.
   서울은 대중교통 비중이 높아 주차가 인구를 덜 설명하고, 경주는 자차 비중이 높아 더 설명할 가능성이 크다 — 전이는 **보수적 방향**(경주에서 과소 추정)으로 틀리므로 "붐빔을 여유로" 오분류 위험이 커진다. 이 점을 §9에 적고 KPI로 감시한다.

## 6. 검증 지표와 통과 기준

정답은 서울시 4등급과 인구 범위 중앙값(대상지별 최대 대비 정규화). 우리 등급 경계는 저장소의 혼잡 경계(75 = 혼잡, `20260908090000`)와 맞춘다:
여유 < 0.25 · 보통 < 0.50 · 약간 붐빔 < 0.75 · 붐빔 ≥ 0.75. `CONGESTION_DATA.md` §8 KPI를 재사용한다.

| 지표 | 정의 | 통과 제안 |
|---|---|---|
| 등급 일치율 | 4등급 정확 일치 | ≥ 50% |
| 인접 등급 일치율 | ±1등급 이내 | ≥ 85% |
| 순위 상관 | Spearman ρ(추정 level, 정규화 인구) — 대상지별·전체 | ≥ 0.5 |
| 위험 오분류율 | 실측 '붐빔'을 '여유'·'보통'으로 표시 | ≤ 5% (§8) |
| 30분 전망 오차 | 추정(t+30) vs 실측(t+30) MAE. 기준선 둘: 지속 모델(현재값 유지) · 서울시 `FCST_PPLTN` | 지속 모델보다 낮을 것. 서울시 예측 대비는 **보고만** |
| 구분 가능률 | 인접 대상지 3곳 등급이 모두 같지 않은 비율 | ≥ 50% (§8) |
| 커버리지 | 추정을 만들 수 있던 (대상지×버킷) 비율 | 보고 |

숫자는 초기 가드레일이고 2주 표본 뒤 조정한다. 통과 못 하면 통과 못 한 대로 대시보드에 남긴다 — 지표를 감추면 §3의 메시지가 무너진다.

## 9. 리스크와 한계 — 발표에서 먼저 말할 것

- **경주 구역 해상도**: 실시간 ITS 주차장 4곳(황리단길 반경 3곳). 추정은 사실상 두 덩어리 관측을 806곳에 펼친 값이다(§10).
  국가 주차정보 API(`PARKING_API_KEY`)가 경주 실시간 면수를 더 주는지 확인해 늘릴 수 있으면 늘린다.
- **서울 → 경주 전이**: 교통 수단 구성이 달라 주차의 설명력이 다르다. 전이 곡선은 경주에서 과소 추정 쪽으로 틀릴 가능성이 있다(§5.3-6).
- **서울 실측도 추정**: 기지국 집계를 격자 가중으로 배분한 값이고 단위가 핫스팟이다. "가게 단위 검증"이라고 말하지 않는다.
- **표본 기간**: 이력이 없어 수집 시작일부터 센다. 심사 전 2주면 주말 2회 — 축제·우천 케이스는 못 들어갈 수 있다.
- **호출 한도**: 미확인. 한도가 낮으면 대상지 수·주기를 줄인다(§4 표).
- **정직성 제약 유지**: 추정치는 `synthetic` 등급 그대로라 모델 학습에 들어가지 않는다(승격 게이트가 `synthetic` 포함 시 거부). 추정을 학습 정답으로 쓰는 순간 §7.2 게이트 전체가 무의미해진다.
