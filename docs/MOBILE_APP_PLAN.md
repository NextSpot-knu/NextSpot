## 0. 요구사항(사용자, 2026-11-01)

1. 지금까지 구현한 NextSpot 을 모바일 앱으로 다시 만든다. 코드 구현은 전부 Claude 가 맡고, 서브에이전트를 적극 써서 시간을 줄인다.
2. 지켜야 할 조건(사용자 제시 단계).
   - ① Expo 세팅, 웹 코드 구조 파악
   - ② 화면 이식 + API 연결, 폰에서 도는 첫 빌드
   - ③ 화면은 RN 컴포넌트로 이식한다 — **WebView 로 감싸기 금지**(애플 반려 사유)
   - ④ 지도를 앱용으로 교체, 위치 권한 처리 + 권한 요청 문구(위치가 왜 필요한지)
   - ⑤ EAS 빌드 → TestFlight·Play 비공개 테스트 업로드(진석 님에게 받은 권한 사용)
   - ⑥ 버그 수정, 심사 대응
3. 이 문서가 정하는 것: 재구현 범위 · 프레임워크 · 작업 방식 · 사용자 검토가 필요한 질문.

## 2. 지금 웹 앱 — 코드 기준 [확인]

조사 에이전트 4개가 웹 화면 목록, 웹 전용 의존성, 공유 가능한 로직, 외부 규정을 나눠 읽었다. 화면 전체 표는 부록 B 에 있다.

**규모와 구조**
- Next.js 16 정적 export · React 19.2.4 · Tailwind v4 · framer-motion · recharts · lucide · sonner · supabase-js. 상태 라이브러리는 없다(화면 state + context 7개).
- 라우트 36개: 관광객·계정 22 · 관제 11 · 사장님 2 · 개발자 1.
- 코드 약 6.1만 줄: `app` 2.59만(관광객 1.58만 · 계정·사장님·개발자 0.32만 · 관제 0.66만) · `components` 1.59만 · `lib` 2.04만(테스트 제외).
- 가장 큰 화면은 `/main` 이다. 페이지 5,159줄에 추천 카드 시트(`RecommendationCard`) 2,325줄과 홈 전용 컴포넌트 1,771줄이 붙는다.
- `lib` 135개 모듈 중 브라우저 API 를 직접 쓰지 않는 모듈은 약 93개다. 그중 import 사슬을 따라가도 브라우저 모듈(API 클라이언트·Supabase 클라이언트·저장소)에 닿지 않는 것은 82개(약 1.1만 줄)다. 예를 들어 `areaDemandCurve.ts`·`postLoginDest.ts` 는 API 클라이언트를, `facilitySearch.ts` 는 Supabase 클라이언트를 import 하고, `cardTimes.ts`·`spotComparison.ts` 는 클라이언트 SPOT 복사본(`recommender.ts` → `shared-types`)을 import 한다.
- 문구: ko·en·ja·zh(간체) 각 1,545키(JSON 1,475 + TS 사전 70), 네 로케일의 키 집합이 같다.
- 관광객 화면이 부르는 API 는 53개다(개발자 전용 3개 포함). Supabase 직접 접근은 `facilities`·`users`·`saved_facilities`·`recommendations`·`inquiries`·`usage_events` 와 RPC 1개다.
- 테스트: `lib` 테스트 131개(그중 57개는 자기 위치 기준 경로로 다른 파일을 읽는 배선 검사), Playwright e2e 39개.

**앱 셸과 핵심 흐름**
- 하단 탭 5개: 홈 `/main` · 저장 `/saved` · 지금 출발하면? `/waiting` · 분산 코스 `/course` · 마이 `/mypage`.
- 첫 방문 때 익명 세션을 자동으로 만든다 → 첫 설정(`/setup`) → 지도와 추천 카드(바로 갈래요 · 킵 · 다시 안 볼래요).
- 수락하면 쿠폰이 나갈 수 있고 카카오맵 길안내가 열린다 → 도착(수동 버튼 또는 30분 뒤) → 방문 확인(체감 혼잡 · 👍👎) → 쿠폰함.

**옮기기 어려운 것**(웹 전용 의존성 조사)
- 지도: 카카오 지도 JS SDK. 홈은 SVG 핀, 화면 좌표 계산으로 핀 겹침 줄이기, HTML 오버레이 12종, CSS 히트맵을 쓴다. 코스는 점선 직선과 번호 핀, 대안 추천은 미니 지도다.
- 저장소: 동기 `localStorage`·`sessionStorage` 를 약 120곳에서 부른다(키 약 48개).
- 스타일: 관광객 화면 className 1,761개. 그리드 101곳, 그라데이션 37곳, 유리 흐림 38곳, `hover:` 252곳, `color-mix` 13곳 같은 RN 에 없는 것이 많다. 그래서 화면 이식은 사실상 JSX·스타일을 다시 쓰는 일이다.
- 움직임: framer-motion 끌기 바텀 시트(3단 스냅), 끌어서 순서 바꾸기.
- 음성: 웹 음성 API(인식·읽기). `/main` 과 `/explore/recommend` 에 따로 구현돼 있다.
- 알림: 화면이 열려 있을 때만 3분 폴링 후 브라우저 알림을 띄운다. 서버 푸시는 없다.

**앱 심사·법규와 맞닿은 사실**
- 앱 안 계정 삭제가 이미 있다: `/mypage/settings` → `DELETE /api/v1/account/me`. 관련 행은 외래 키로 함께 지워진다. 화면은 가입 계정에만 버튼을 보이지만, API 는 게스트(익명 세션)도 부를 수 있다.
- 개인정보 안내는 로그인 없이 공개 URL(`/mypage/privacy`)로 열린다. 다만 위치 정보 처리, Upstage LLM, 로그인 제공자 프로필, 처리자·국외 이전(API 오리건 · DB 싱가포르 · Vercel), 개인정보 보호책임자, 보유기간·파기, 만 14세 미만 처리가 적혀 있지 않다. 법률 검토도 대기 중이다(HANDOVER 10-31c ⑥).
- 위치 정보가 서버 쪽에 남는 곳이 있다.
  - `recommendations` 표에 좌표 열은 없다. 하지만 후보별 거리(`recommendation_snapshot.distance_m`)를 사용자 id 와 함께 저장한다. 위치를 아는 여러 시설까지의 거리라 요청 시점 위치를 되짚을 수 있다.
  - 화장실·주차장 조회는 사용자 좌표를 GET 쿼리로 보낸다. API(uvicorn)의 접속 로그가 켜져 있어 쿼리가 로그에 남는다.
- 고객 문의는 로그인 없이 보낼 수 있다. 하지만 이메일 칸이 없고 답은 앱 안에서만 보인다. 공개 연락 이메일도 없다. -> 이메일 남기라고 하든가 고객 문의는 로그인해서 하라고 하는 쪽으로 나중에 수정
  - 답(Claude): 기록했다. 권장은 **게스트 문의에 '답 받을 이메일(선택)' 칸 + 수집 목적 한 줄**이다. 로그인을 필수로 하면 게스트(대부분의 사용자)가 문의할 길이 없어진다. 앱 문의 화면(2단계 마이페이지 묶음)에 같이 넣고 웹도 맞춘다 — 다른 뜻이면 알려 주세요.
- 다른 사용자에게 보이는 사용자 콘텐츠는 사장님 가게 사진(바로 공개, 관리자가 사후에 내림)과 타임세일·좌석 배지다. 관광객 제보는 집계 숫자로만 보인다. 사용자용 신고·차단 기능은 없다.
- Apple 로그인이 없다(카카오·구글만). 카카오 로그인은 비즈 앱 전환 전이라 지금 막혀 있다(KOE205 — HANDOVER 사람 작업 '카카오 개발자 콘솔').
- 비밀번호 재설정·가입 확인 메일은 PKCE 코드 교환으로만 처리한다(`verifyOtp` 경로 없음). 그래서 메일을 요청한 브라우저가 아닌 다른 기기·브라우저에서 링크를 열면 실패한다 — 지금 웹에도 있는 문제다.
- 위치는 화면을 열 때 한 번 읽는다(`getCurrentPosition`). 경주 범위 밖이면 황리단길 중심으로 옮기고 한 번 안내한다. 도착 확인은 GPS 를 쓰지 않는다.
- 검색 결과가 0건이면 검색어를 LLM(Upstage)으로 다시 써서 찾는 경로가 있다(LLM 전체 스위치가 켜져 있을 때).
- Turnstile CAPTCHA 코드는 있지만 꺼져 있다(사이트 키 없음, Supabase CAPTCHA 꺼짐 — HANDOVER 10-31c ⑤). 익명 로그인 IP 한도는 300/h 로 올려 둔 상태다.
- 심사(공모전)용 잔재가 남아 있다: 심사 계정 안내(`JudgeAccountHint`), `?demo=1` 콘솔, 데모 조작 패널, 가정 시각 프리셋, 클라이언트 SPOT 복사본(`lib/recommender.ts`).

## 5. 코드 구조와 공유 [제안]

### 5.1 저장소 배치

- `apps/mobile` 에 둔다. 루트 `package.json` 의 workspaces 를 `["apps/*","packages/*"]` 에서 `["apps/web","packages/*"]` 로 바꿔 앱을 작업공간에서 뺀다. 루트 lock 에 옛 globs 가 저장돼 있으므로 같은 커밋에서 lock 도 다시 만든다. 빼는 이유:
  - 웹은 react 19.2.4, SDK 57 은 react 19.2.3 이다. RN 은 렌더러와 react 버전이 정확히 같아야 하고, Expo 모노레포 문서도 한 앱 안의 React 중복은 실행 오류를 낸다고 경고한다 [확인·조사].
  - 작업공간에 넣으면 루트 lock 에 Expo·RN 의존성 트리가 통째로 들어간다. Vercel(루트 `npm install`)과 CI 의 웹 설치가 느려지고, 피어 의존성 충돌이 나면 웹 배포가 깨진다 [확인].
  - 루트로 올라온 `@types/react` 두 벌이 웹 `tsc` 에 섞일 수 있다 [확인].
- 대가: Expo 의 모노레포 자동 Metro 설정이 적용되지 않는다. 그래서 웹 코드를 읽는 해석 설정을 직접 한다(§5.2).
- `apps/mobile` 은 자기 `package-lock.json` 을 가진 독립 npm 프로젝트다. CI 에는 `mobile` 잡을 따로 둔다(그 폴더에서 `npm ci`, lock 기준 캐시).
- 네이티브 폴더(`ios/`·`android/`)는 커밋하지 않는다. 설정(`app.config.ts`)에서 생성한다(Expo CNG). `.gitignore` 에 `.expo/`·`ios/`·`android/`, 서명 키(`*.p8`·`*.jks`·`*.keystore`), 서비스 계정 JSON 을 넣는다.

### 5.2 웹 코드 재사용

- **순수 모듈(의존까지 순수한 82개)은 복사하지 않고 import 한다.** 해석 설정은 1단계의 첫 끝 조건이다.
  - `metro.config.js`: `watchFolders` 에 웹 `lib` 와 `packages/shared-types` 를 넣고, `resolver.nodeModulesPaths` 를 `apps/mobile/node_modules` 하나로, `disableHierarchicalLookup: true` 로 둔다. 웹 파일이 루트 `node_modules` 의 다른 사본(예: supabase-js 두 벌)을 집지 못하게 하기 위해서다.
  - 앱 `package.json` 에 `"shared-types": "file:../../packages/shared-types"` 와 supabase-js 를 직접 적는다. TS `paths` 는 `@/*` → `../web/*` 와 `shared-types` 를 맞춘다.
  - **어댑터 바꿔 끼우기**: Metro `resolver.resolveRequest` 에 '해석된 파일 경로 기준' 치환표를 둔다. 웹의 `lib/supabase`·`api-client`·`auth`·`turnstile`·`usageEvents` 같은 브라우저 모듈은 `@/lib/x` 로 오든 `./x` 로 오든 `apps/mobile/lib/adapters/*` 로 간다. 그래야 Supabase 클라이언트가 두 개 생기거나(토큰 갱신이 겹친다) 자리값 주소로 조용히 실패하는 일이 없다.
  - **RN 은 `window` 를 정의한다**(`window = globalThis`). 웹 모듈의 `typeof window !== 'undefined'` 검사가 참이 되어 `window.location.origin` 같은 줄이 오류를 낸다. 그래서 허용 목록 검사는 모듈 하나가 아니라 **의존 폐포 전체**에 대해 `window.`·`document.`·`CustomEvent`·`DOMException` 사용과 앱 `package.json` 에 없는 패키지 import 를 막는다.
  - 검증: 깨끗한 체크아웃에서 `apps/mobile` 만 설치하고 `tsc` + `expo export` 가 통과해야 한다(CI·EAS 와 같은 조건).
  - 웹 쪽 작은 정리를 허용한다. 예: `displayWalkingMinutes` 를 `recommender.ts` 밖으로 빼 SPOT 복사본이 앱 번들에 끌려오지 않게 한다. 웹을 고치면 웹 게이트를 함께 돌린다.
  - 모듈을 패키지로 옮기지 않는 이유: 웹 테스트 57개가 자기 위치 기준 경로로 다른 파일을 읽어(배선 검사) 옮기면 깨진다.
- **저장소에 묶인 모듈.** 앱 진입 파일이 `expo-router/entry` 보다 먼저 전역 `localStorage`(expo-sqlite)와 `sessionStorage` 대역을 설치한다. 그러면 저장소만 쓰는 웹 모듈은 그대로 돌 가능성이 크다 [추정 — 1단계에서 확인]. 환경 변수·Supabase·브라우저 이벤트를 쓰는 모듈만 어댑터로 다시 쓴다. 다시 쓴 파일은 머리에 웹 원본 경로와 기준 커밋을 적고, `apps/mobile/PORTING.md` 표로 원본이 바뀌었는지 추적한다.
- **문구는 웹 JSON 을 그대로 읽는다.** 앱에만 필요한 문구(권한 안내 등)는 같은 JSON 의 `app.*` 절에 넣는다. 그러면 웹의 4로케일 짝 검사(`parity.test.ts`)를 그대로 받는다. 웹 키 검사(`scripts/check-i18n-keys.mjs`)의 범위에 `apps/mobile` 을 더해, 웹에서 안 쓰는 키를 정리하다 앱 키를 지우지 않게 한다.
- **환경 변수.** Expo 는 `EXPO_PUBLIC_*` 만 번들에 넣는다. 어댑터가 앱 설정 모듈에서 값을 읽는다. `EXPO_PUBLIC_*` 에는 API 주소·Supabase 주소·anon 키처럼 원래 공개인 값만 넣는다. 번들에 그대로 들어가기 때문이다. 웹 `.env.local` 에만 있고 코드가 읽지 않는 공개 변수는 옮기지 않는다.

### 6.2 위치 권한 흐름

Apple 디자인 가이드(HIG)는 시스템 창 앞의 안내 화면에 **버튼 하나**('계속')만 두고, 그 버튼이 시스템 창을 열게 하라고 한다. '나중에' 같은 빠져나가는 버튼은 넣지 말라고 한다(법적 동의가 필요할 때만 예외) [조사]. 그래서 흐름은 이렇다.

1. (M20 이 '필요'면) 첫 실행 때 위치정보 이용약관 동의 화면을 먼저 보인다. 이것은 법적 동의라 '동의' · '동의 안 함' 두 버튼을 둔다. 동의하지 않으면 위치를 쓰지 않고 황리단길 중심으로 추천한다.
2. 첫 설정을 마치고 홈에 처음 들어올 때 안내 화면을 보인다. 왜 필요한지 설명하고 버튼은 '계속' 하나다. 누르면 `requestForegroundPermissionsAsync`(앱을 쓰는 동안)를 부른다. 백그라운드 위치는 요청하지 않는다.
3. 시스템 창에서 거부하면 황리단길 중심으로 추천한다. 홈 위에 닫을 수 있는 배너 '내 주변 추천 켜기'를 두고, 누르면 설정 앱으로 보낸다. iOS 는 한 번 거부하면 시스템 창이 다시 뜨지 않는다.
4. 대략적 위치만 허용한 경우(iOS 14+·안드로이드 12+) 정확도가 1km 보다 나쁘면 황리단길 중심 기준으로 추천하고 '정확한 위치를 켜면 더 가까운 곳을 찾아요'를 배너로 안내한다. 경주 시내는 좁아서 수 km 오차면 추천이 어긋나기 때문이다.
5. 경주 범위 밖이면 지금 웹 규칙 그대로다(황리단길 중심 + 한 번 안내). 해외 심사자도 이 화면을 보므로 심사 메모에 적는다(§8.3).
6. 위치는 홈·대안 추천·코스를 열 때 한 번씩 읽는다. 계속 추적하지 않는다(지금 웹과 같다).

### 6.3 권한 요청 문구 — 검토 요청

iOS 시스템 창 문구(`NSLocationWhenInUseUsageDescription`)다. expo-location 플러그인의 `locationWhenInUsePermission` 으로 넣는다. 플러그인은 쓰지 않는 키(`locationAlwaysAndWhenInUsePermission`·`locationAlwaysPermission`·`motionUsagePermission`)에도 일반 기본 문구를 넣으므로 셋 다 직접 정하고, `isAndroidBackgroundLocationEnabled`·`isAndroidForegroundServiceEnabled` 는 false 로 둔다. 4로케일은 `locales` 파일과 `CFBundleAllowMixedLocalizations` 로 현지화하고, 중국어 키는 iOS 언어 ID 인 `zh-Hans` 로 쓴다 [조사]. 안드로이드는 시스템 창에 앱 문구가 없으므로 §6.2 ②의 안내 화면에 같은 뜻을 쓴다. 앱 말투(해요체)에 맞췄다.

| 로케일 | 문구(초안) |
|---|---|
| ko | 현재 위치 근처에서 덜 붐비는 곳을 추천하고 걸어서 가는 시간을 계산하는 데 위치를 사용해요. 예를 들어 지금 있는 곳에서 걸어서 10분 안에 갈 수 있는 한산한 장소를 보여 드려요. |
| en | NextSpot uses your location to recommend less crowded places near you and to estimate walking times. For example, it shows quiet places within a 10-minute walk of where you are. |
| ja | 現在地の近くで混雑の少ない場所をおすすめし、徒歩での所要時間を計算するために位置情報を使用します。たとえば、今いる場所から徒歩10分以内で行ける空いている場所を表示します。 |
| zh-Hans | NextSpot 使用您的位置来推荐附近人少的地方，并计算步行所需时间。例如，显示从您当前位置步行10分钟内可到达的空闲地点。 |

앱 안 안내 화면(ko 초안, 4로케일은 i18n 단계에서 한 번에 쓴다):
- 제목: 내 주변에서 덜 붐비는 곳을 찾을게요
- 본문: 위치를 허용하면 지금 있는 곳에서 걸어갈 수 있는 한산한 장소를 먼저 보여 드려요. 허용하지 않아도 황리단길 중심으로 추천해요.
- 버튼: 계속(하나만)

'이동 기록을 저장하지 않아요' 같은 저장 관련 약속은 넣지 않는다. 지금은 접속 로그와 추천 기록의 거리 값으로 위치가 남기 때문이다(§2). 줄이는 작업은 M22, 알리는 곳은 개인정보 안내다. v1 은 위치 말고 다른 권한(카메라·사진·마이크·알림)을 요청하지 않는다.

## 7. 인증·계정·API [제안]

### 7.1 게스트

앱을 켜면 지금 웹(`SessionBootstrap`)처럼 익명 세션을 만든다. 실패하면 5초·15초·45초·2분·5분 간격으로 다시 시도한다. 웹의 화면 보임 이벤트 대신 앱 활성 상태(AppState)로 재시도와 토큰 갱신을 건다. Supabase 클라이언트는 공식 안내대로 `storage: localStorage`(expo-sqlite)·`detectSessionInUrl: false` 로 만들고, 웹과 같이 `flowType: 'pkce'` 를 쓴다(supabase-js 기본값은 implicit 이다) [조사].

### 7.2 로그인

- **이메일 로그인·가입**: 웹 `lib/auth.ts` 의 이메일 함수를 앱 어댑터로 옮긴다(웹 파일은 `window.location.origin` 을 써서 그대로는 못 쓴다).
- **재설정·가입 확인 메일(H4)**: PKCE 코드 교환은 요청을 시작한 같은 기기·같은 브라우저에서만 된다 [조사]. 앱에서 보낸 메일을 웹에서 열면 매번 실패하고, 지금 웹도 다른 기기에서 열면 실패한다.
  - 권장: Supabase 메일 템플릿을 `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=…` 꼴로 바꾸고(사람 — 대시보드), 웹에 `verifyOtp` 로 처리하는 `/auth/confirm` 페이지를 더한다(Claude — 웹). 그러면 어느 기기에서 열어도 재설정·확인이 된다.
  - 대안: `nextspot://auth/reset` 딥링크로 앱 안에서 재설정한다(앱이 없는 기기에서는 안 된다).
  - iOS v1 은 이메일이 유일한 가입 수단이라 이것을 2단계 전에 고친다.
- **구글·카카오 OAuth**: `signInWithOAuth`(`redirectTo: nextspot://auth/callback`, 브라우저 자동 이동 끔) → `WebBrowser.openAuthSessionAsync` → `exchangeCodeForSession`. 안드로이드에서는 Expo Router 가 같은 딥링크를 자동으로 받아, 일회용 코드를 두 번 교환하려다 오류가 나거나 게스트 합치기가 두 번 돌 수 있다 [조사]. 교환은 한 곳(콜백 라우트)에서만 하고 `+native-intent` 로 중복을 막는다. 안드로이드 실기기 확인 항목에 넣는다. 이미 연결된 계정의 재시도와 게스트 데이터 합치기는 웹 로직을 재사용한다.
- **App Store 4.8**: 구글·카카오 같은 제3자 로그인을 주 계정 로그인으로 쓰면, 이름·이메일만 받고 이메일을 숨길 수 있으며 광고 추적을 하지 않는 로그인(사실상 Apple 로그인)을 함께 줘야 한다. 자체 계정(이메일)만 쓰는 앱은 예외다 [조사].
- Apple 로그인을 넣으면 **계정을 지울 때 Apple 토큰을 REST API 로 철회해야 한다** [조사]. 로그인 때 받은 인증 코드를 서버가 refresh token 으로 바꿔 보관했다가 삭제 때 철회하는 API 작업이 생긴다. 진석 님 계정에서 Sign in with Apple 키도 만들어야 한다.
- **권장안(M3)**: v1 은 이메일 + 게스트 + 안드로이드 구글로 낸다. iOS 의 구글·Apple 은 철회 작업과 함께 v1.1 에 넣는다. 조건이 있다.
  - iOS 빌드에는 구글·카카오 버튼, 계정 연결(`linkIdentity`), '구글로 계속하기' 경로가 하나도 보이지 않아야 한다(`Platform.OS` 게이트 + 테스트).
  - 웹에서 구글로 가입한 사람은 v1.1 전까지 iOS 앱에서 그 계정으로 로그인하지 못한다(게스트·이메일은 된다). 앱 안과 스토어 소개에 알린다.
  - 처음부터 iOS 에도 넣으면 약 1일과 사람 작업(키·Supabase 설정)이 더 든다.
- **카카오**는 비즈 앱 전환(사람 작업) 전까지 막혀 있다. v1 에서는 버튼을 숨긴다. 전환 뒤에는 브라우저 OAuth(웹과 같은 REST 키)로 켠다. 카카오톡 앱으로 바로 로그인하는 네이티브 방식은 Supabase 가 네이티브 앱 키를 함께 받아 주는지(토큰의 `aud`) 확인이 필요해 뒤로 미룬다 [조사·재확인].

### 7.3 계정 삭제

- 가입 계정: 설정 화면에서 지금 API 를 그대로 부른다. App Store 는 앱 안에서 찾기 쉬운 곳에 두고, 비활성화가 아니라 계정과 개인정보를 실제로 지우라고 한다. 지금 API 가 그렇게 한다 [조사·확인].
- 게스트: 같은 API 를 게스트도 부를 수 있다. 앱 설정에 '내 데이터 삭제'를 두어 서버 쪽 게스트 데이터까지 지운다(지금 웹의 '데이터 초기화'는 기기 안만 지운다). 데이터 보안 답과 파기 원칙에 유리하다.
- Google Play: 앱 안 삭제와 함께, 앱을 다시 깔지 않고도 삭제를 요청할 수 있는 **공개 웹 페이지**가 필요하다 [조사]. 웹 `/mypage/settings` 는 로그아웃 상태로 열면 익명 세션이 생겨 '데이터 초기화'만 보이므로 모자란다. 4단계 전에 웹에 공개 안내 페이지를 만든다. 담을 것:
  - 앱 이름·개발자 이름, 앱 안 경로, 웹 경로, 이메일 요청 주소(M13)
  - 지워지는 것(계정과 외래 키로 이어진 행)
  - 남는 것과 기간: 익명 사용 기록 1년, 게스트 네트워크 해시 30일, 서버 로그(M22 결과에 따라)
  - 처리 기한

### 7.4 역할

사장님·관제·개발자 계정도 앱에서는 관광객 화면을 본다. 콘솔은 마이페이지의 '웹에서 열기' 링크(시스템 브라우저)로 연다.

### 7.6 CAPTCHA(M7)

Supabase CAPTCHA 는 프로젝트 전체에 걸린다. 켜면 앱의 익명 로그인·이메일 로그인·가입·재설정이 토큰 없이 거절된다. Cloudflare 문서도 Turnstile 은 네이티브로 돌지 않아 WebView 로 띄워야 한다고 적는다 [조사].
- **권장: 앱 출시 전까지 Supabase CAPTCHA 를 켜지 않는다.** HANDOVER 10-31c ⑤('Turnstile 켜기')를 보류한다.
- 남용은 익명 로그인 IP 한도와 API 한도로 막는다. 다만 익명 로그인 한도를 지금 300/h 로 올려 둔 상태라 약하다. 앱 출시 전에 낮출지 함께 정한다.
- 나중에 더 막아야 하면 서버가 기기 증명(App Attest·Play Integrity)을 확인하고 세션을 내주는 방식을 따로 설계한다. 작업이 크다.

## 8. 스토어 출시 준비 [제안] — 요구 ⑤

### 8.1 진석 님에게 받을 권한·자원(사람 작업)

키 파일(.p8·서비스 계정 JSON)은 저장소와 채팅에 올리지 않는다. 저장소 밖 로컬 폴더에 두고 경로만 알려 주면 Claude 가 `eas credentials`·`eas submit` 에 쓴다.

**Apple — iOS 실기기 확인을 당기려면 2단계 전에(M5)**
- App Store Connect 팀 초대. 앱 레코드를 만들고 TestFlight 를 관리할 수 있는 역할이 필요하다.
- App Store Connect API 키(.p8 · Key ID · Issuer ID). API 접근 요청은 계정 소유자(Account Holder)만 할 수 있다. Expo 안내는 Admin 역할 키를 권한다(App Manager 로 충분한지는 [재확인]) [조사]. 이 키로 EAS 가 인증서·프로비저닝·업로드를 처리한다.
- 번들 ID 등록. EAS 가 대신 할 수 있다.
- TestFlight 내부 테스터 목록(App Store Connect 사용자, 최대 100명, 심사 없음). 외부 테스터(최대 1만 명)는 첫 빌드가 베타 심사를 거친다 [조사].
- (iOS 소셜을 넣을 때) Sign in with Apple 키.

**Google — 4단계 전에**
- Play Console 사용자 초대. 앱 만들기와 출시 관리 권한이 필요하다.
- Play Console 에 앱을 먼저 만든다(패키지명은 M4). 현재 Expo 문서로는 첫 업로드를 손으로 할 필요 없이 `eas submit` 이 내부 테스트 트랙에 첫 릴리스를 만든다 [조사·재확인].
- Google Cloud 서비스 계정 JSON(EAS Submit 용). Play Console 권한은 Admin 이 아니라 테스트 트랙·출시·스토어 정보 관리 권한이면 된다 [조사].
- 비공개 테스트 테스터 이메일 목록(또는 Google 그룹).
- 계정 종류와 만든 날짜(M5). **2023-11-13 이후 만든 개인 계정은 프로덕션 출시 전에 테스터 12명 이상이 14일 연속 비공개 테스트에 참여해야 하고**, 그 뒤 출시 신청 검토(보통 7일 안)가 있다. 조직 계정(D-U-N-S 번호 필요)은 이 조건이 없다 [조사].

**그 밖**
- Expo 조직(EAS 프로젝트 소유자). 사용자 계정을 권장하고 진석 님을 초대한다(M6). 1단계 끝 첫 안드로이드 빌드에 필요하다.
- 안드로이드용 Google Maps API 키(M21). Expo Go 만 Expo 의 키를 쓰고, 개발·preview·스토어 빌드는 우리 키가 필요하다. 1단계에 필요하다. Google Cloud 프로젝트와 결제 계정 연결이 필요하고, 패키지명과 **서명 SHA-1 두 개**(EAS 업로드 키, Play 앱 서명 키)로 제한한다. 하나만 넣으면 Play 로 받은 앱의 지도가 회색으로 나온다.
- Supabase 대시보드: §7.5 의 Redirect URL, 메일 템플릿(과 iOS 소셜을 넣을 때 Apple 제공자).

## 9. 작업 방식 [제안] — 요구 ①~⑥, 서브에이전트

### 9.1 원칙

- **메인 세션**은 나누기·통합·검증·커밋·푸시를 맡는다. **에이전트**는 겹치지 않는 폴더를 맡아 구현하고 커밋까지만 한다(worktree 격리). 푸시는 메인 세션만 한다.
- 공용 층(디자인 시스템·지도 래퍼·어댑터)을 먼저 만들고 그 위에서 화면을 병렬로 옮긴다. 같은 파일을 두 에이전트가 동시에 고치지 않는다.
- **i18n(4로케일 문구)은 나눠 맡기지 않는다.** 화면 에이전트는 있는 키만 쓰고 새 키는 요청 목록 파일에 적는다. 통합 때 에이전트 하나가 4로케일을 한 번에 쓴다.
- **자기 코드는 자기가 검토하지 않는다.** 웨이브마다 렌즈가 다른 검토 에이전트 셋을 돌린다: 웹 동작 일치 · 플랫폼·심사·법규 · 문구·접근성·디자인 원칙. 지적은 그 파일을 맡은 에이전트가 고치고, 높음·중간이 0 이 될 때까지 다시 본다.
- **화면별 이식 점검표**
  - 로딩·빈·오류 상태
  - 게스트·가입 계정
  - 4로케일
  - 작은 화면(360pt)·큰 글자, 폴더블 접힘·펼침 전환(사용자 기기 Z Fold7 — 펼친 화면은 태블릿 폭이라 내용 최대 폭을 두고 가운데 정렬)
  - 접근성 라벨, 탭 영역 44pt([`DESIGN_PRINCIPLES.md`](./DESIGN_PRINCIPLES.md))
  - 웹 Playwright e2e 39개에 적힌 기대 동작
- **스타일 대체 규칙**(디자인 시스템 에이전트가 먼저 정하고 화면 에이전트에게 준다): 그리드 → flex-wrap, 그라데이션 → expo-linear-gradient, 유리 흐림 → expo-blur(안드로이드 반투명), `hover:` → 버림, `color-mix` → 토큰을 미리 계산한 hex, 글자 스타일 → Text 에 직접.
- **앱 게이트**
  - typecheck
  - lint(WebView import 금지 포함)
  - 테스트(웹 순수 모듈 테스트 + 앱 로직 테스트)
  - 문구 키 검사(웹 검사 범위에 `apps/mobile` 포함)
  - 공유 모듈 의존 폐포 검사(§5.2)
  - `expo-doctor`(의존성 호환)
  - `expo export`(iOS·안드로이드 번들 확인, 깨끗한 설치 기준)
  - 웹·API 게이트는 바뀐 쪽만 지금처럼 돌린다.
- **작업 브랜치**는 지금 규칙대로 `yunseong` 이다. 작업 하나마다 게이트 → 커밋 → 푸시한다. main 반영은 지시가 있을 때만 한다.

- **호환 확인(반나절)**: SDK 57 빈 앱에 실제로 촘촘한 컴포넌트 두 개(추천 카드 머리, 칩 줄)를 NativeWind·Uniwind 로 각각 옮겨 본다. 바텀 시트, 지도, 토스트, expo-sqlite `localStorage`, Hermes `Intl` 시간대(`Asia/Seoul`)도 띄운다. 막히는 것이 있으면 그 라이브러리를 대안으로 바꾼다(§4 대안 열).
- 메인 세션이 할 일:
  - `create-expo-app`(TypeScript · Expo Router 탭), workspaces 조정과 루트 lock 재생성
  - **해석 설정(§5.2)** — Metro `watchFolders`·`nodeModulesPaths`·어댑터 치환표, TS `paths`, 의존 폐포 검사. 깨끗한 체크아웃에서 `apps/mobile` 만 설치해 `tsc`·`expo export` 가 통과하는 것이 첫 끝 조건이다.
  - 진입 파일(저장소 대역 설치), 환경 설정, Supabase·API 클라이언트 어댑터
  - 문구 제공자(웹 JSON + 기기 언어), 계정·세션·공개 설정 제공자
  - 빈 탭 5개, CI `mobile` 잡, `eas.json` 뼈대
- 에이전트 A — 디자인 시스템: 웹 토큰(`globals.css`)을 TS 토큰으로 옮긴다(색은 hex 로 미리 계산). §9.1 스타일 대체 규칙을 정한다. 버튼·칩·카드·시트 래퍼·토스트·아이콘·빈/오류 상태·스켈레톤을 만들고, 한국어 줄바꿈(iOS `hangul-word`)과 글꼴을 맞춘다.
- 에이전트 B — 지도 래퍼(§6.1): 핀·겹침 줄이기·원·점선·내 위치·카메라를 만들고 순수 계산 테스트를 붙인다.
- 에이전트 C — 플랫폼 어댑터: 사용 기록(운영 빌드만), 화면 보임 대신 AppState, 카카오맵 링크, 공유·클립보드·진동, 이미지 https 처리.
- **첫 폰 실행**은 이 단계 끝이 목표다. 사용자 폰은 Galaxy Z Fold7(안드로이드)이라 Apple 권한 없이 된다(A15). EAS 개발 빌드 설치 링크(APK)로 받는다. Expo 계정(M6)·패키지명(M4)·안드로이드 지도 키(M21)가 있으면 되고, Google Play 계정은 필요 없다. 이 PC 에는 Android Studio 에뮬레이터를 깔아(A15 허락) 일반 폰과 폴더블 기기 프로필을 만들고, 에이전트가 화면을 직접 캡처해 확인한다.

- 웨이브가 끝나면 메인 세션이 worktree 를 하나씩 합치고 전체 게이트를 돌린다. 그다음 i18n 에이전트 하나가 새 키를 4로케일로 쓰고, 검토 3렌즈 → 수정을 반복한다.
- 홈과 추천 카드가 가장 크다. 둘을 먼저 시작하고, 나머지는 공용 층이 준비되는 대로 붙인다.

**3단계 — 지도·위치 마무리**
- 권한 흐름(§6.2), 권한 문구 4로케일(§6.3), 위치정보 동의 화면(M20), 안드로이드 OAuth 복귀 중복 확인(§7.2).
- iOS 실기기는 진석 님 권한이 온 뒤 TestFlight 내부 테스트로 본다. 개발 빌드(기기 UDID 등록, 연 100대까지)도 가능하다 [조사].

**4단계 — EAS 빌드 → TestFlight·Play**
- 빌드 프로필은 셋이다: `development`(개발 클라이언트) · `preview`(내부 배포) · `production`(스토어). 버전 번호는 EAS 원격 버전 관리로 자동으로 올린다.
- 아이콘·스플래시·안드로이드 적응형 아이콘, 피처 그래픽을 만든다. 스토어 자료 초안은 소개 문구(ko·en), 개인정보 라벨·데이터 보안 답(§8.4), 콘텐츠 등급 답, 심사 메모(§8.3)다.
- API·웹 변경(§7.5의 '4단계 전' 줄)을 KST 밤에 반영한다.
- 목표는 둘로 나눈다.
  - ① **내부 테스트**: `eas build --platform all --profile production` → `eas submit`. iOS 는 업로드 뒤 10~15분이면 TestFlight 내부 테스트에 보인다. 안드로이드는 Play 내부 테스트 트랙(최대 100명, 표준 심사 생략 가능) [조사]. 스토어 심사가 거의 없어 빠르다.
  - ② **비공개·외부 테스트**: Play 비공개 테스트와 TestFlight 외부 테스트는 스토어 자료·데이터 보안·개인정보 처리방침·삭제 안내 페이지와 법무 확인(M13·M20)이 끝난 뒤 올린다. 새 앱의 첫 검토는 며칠 걸릴 수 있다.
- 안드로이드는 Play Console 에 앱을 먼저 만들어 둔다(사람). 스토어 등록 정보를 다 채울 때까지 첫 릴리스는 초안 상태다 [조사].

**5단계 — 버그 수정·심사 대응**
- 테스터 피드백은 GitHub 이슈 템플릿 '앱 버그'(기기·OS·빌드 번호·재현 순서·스크린샷)로 받는다.
- 메인 세션이 분류해 수정 에이전트에게 나눈다. JS 만 바뀌면 EAS Update 로 바로 내보낸다(M11). 네이티브가 바뀌면 새 빌드를 올린다.
- 심사 반려: Claude 가 답변 초안과 코드 수정을 만들고, 사람이 App Store Connect·Play Console 에서 답을 보낸다.

### 9.4 기간 추정 [추정]

- 에이전트 작업만 보면 1~3단계가 약 5~7일이다. 웹 화면 코드 약 2만 줄을 7개 묶음으로 병렬로 다시 쓰고(스타일은 사실상 재작성), 검토·수정을 2~3회 도는 기준이다.
- **① TestFlight 내부·Play 내부 테스트까지 약 1.5~2주**다. 답과 계정 권한(Expo·Apple·Google·지도 키)이 제때 오는 것이 전제다.
- **② Play 비공개·TestFlight 외부 테스트**는 스토어 자료와 법무(위치정보법 신고·동의, 개인정보 처리방침) 확인이 끝나야 올린다. 법무 일정에 달려 있다.
- Play 프로덕션 출시는 개인 계정이면 테스터 12명 × 14일 연속 테스트 + 출시 신청 검토(보통 7일 안)가 더 붙는다(M5). 테스터는 일찍 모은다.
- EAS 무료 플랜은 월 안드로이드 15회·iOS 15회 빌드와 낮은 우선순위 대기열이다. 다 쓰면 다음 달까지 빌드가 막힌다. 바쁜 주에는 Starter(월 19달러)를 고려한다 [조사].

### 9.5 웹과 앱을 같이 고치는 규칙(M16)

- 기준 커밋 이후 관광객 화면을 바꾸는 웹 커밋은 본문에 '앱: 반영 필요 / 불필요'를 적는다. 필요하면 같은 세션에서 앱도 고친다. 이 규칙을 `AGENTS.md` 에 넣는다.
- 앱이 import 하는 웹 순수 모듈을 고치면 앱 게이트도 돈다(의존 폐포 검사가 브라우저 API 유입을 잡는다).
- 앱은 사용자가 업데이트하기 전까지 옛 버전이 남는다. API 는 옛 버전과 호환을 지키고, 깨질 때는 최소 앱 버전으로 업데이트를 안내한다(§7.5).
